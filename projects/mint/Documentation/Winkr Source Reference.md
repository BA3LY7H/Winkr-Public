## 1. Overview

### What Winkr Is

Winkr is an unlocker/modloader for World of Warcraft. It consists of:

1. **winkr.dll** — Injected into the WoW process. Provides direct memory reading, object enumeration, and registers Lua global functions that mods can call.
2. **winkr_gui.exe** — External GUI that communicates with the DLL via IPC shared memory. Also performs OM enumeration via `ReadProcessMemory`.

The DLL hooks WoW's main thread message loop via `WH_GETMESSAGE`, detects Lua state creation, and injects mod code at the right lifecycle point.

### How the Bridge Works

C functions are registered as Lua globals in `ExecuteModsOnMainThread()` (winkr_mods.c, line ~272) using:

```c
pPushCClosure(L, (void*)winkr_FunctionName, 0);
pSetField(L, LUA_GLOBALSINDEX, "winkr_LuaName");
```

This uses a vendored Lua library (`wk_lua_pushcclosure` / `wk_lua_setfield`) that operates on WoW's own `lua_State*`. The functions use `__fastcall` convention and accept `void* L` (the Lua state pointer).

### Stack Reading

Winkr uses **direct stack reading** (calibrated at load time in `CalibrateDirectStackRead`) to read Lua arguments without calling WoW's Lua API. This avoids re-entrancy issues and is faster. Key helpers:

| Helper | Purpose |
|---|---|
| `wk_arg_number(L, idx)` | Read number from Lua stack slot |
| `wk_arg_string(L, idx, &len)` | Read string from Lua stack slot |
| `wk_arg_bool(L, idx)` | Read boolean from Lua stack slot |
| `wk_arg_is_nil(L, idx)` | Check if stack slot is nil |
| `winkr_read_stack_number(L, idx)` | Alias for `wk_arg_number` |
| `winkr_gettop_inline(L)` | Get stack top (number of args) |

TValue size is runtime-calibrated (candidates: 16, 24, 32 bytes; WoW typically uses 24).

## 3. Object Manager Internals

### Architecture

The OM uses a **split architecture**:
- **GUI process** enumerates objects via `ReadProcessMemory` and populates the IPC shared memory cache
- **DLL (in-process)** reads the IPC cache for GUID lookups, and does direct memory reads for real-time data (position, facing, auras)

### IPC Shared Memory (`WinkrIPC`)

The shared memory structure (`ipc_protocol.h`) contains:
- **Header**: magic (`0x574B5200` = "WKR\0"), version, DLL status
- **Global GUIDs**: active player, target, focus, mouseover (lo/hi pairs)
- **OM cache**: `OmCacheEntry objects[2048]` (MAX_OM_OBJECTS = 2048)
- **Seqlock**: `om_enum_seq` — odd = writing (enumeration in progress), even = stable
- **Rolling log buffer**: 16KB ring buffer for debug output

### Object Enumeration (winkr_om_enum.c)

`DLL_EnumerateOM()` walks the EntityRegistry:

1. **Entry point**: `g_pEntityRegistry` (RVA in WoW's data segment)
2. **Record format**: 16-byte entries `[flags:4, pad:4, entity*:8]`
3. **Entity → CGObject**: `entity+8` → archetype, `archetype+0x38` → CGObject offset
4. **Position**: `archetype+0x34` → position component offset → entity+posOffset+0x84/0x88/0x8C
5. **GUID**: CGObject+0x10 (lo), CGObject+0x18 (hi)
6. **Type byte**: CGObject+0x24

**Tracked object types** (others are ignored):
- `CGTYPE_UNIT` (5)
- `CGTYPE_PLAYER` (6)
- `CGTYPE_ACTIVE_PLAYER` (7)
- `CGTYPE_GAMEOBJECT` (8)
- `CGTYPE_DYNAMIC_OBJ` (9)
- `CGTYPE_CORPSE` (10)
- `CGTYPE_AREA_TRIGGER` (11)

### GUID Format

WoW GUIDs are **128-bit** (two uint64s: lo + hi). Formatted as typed strings like:
- `Player-XXXX-XXXXXXXX`
- `Creature-0-XXXX-XXXX-XXXX-XXXXXXXXXX`
- `GameObject-0-XXXX-XXXX-XXXX-XXXXXXXXXX`

The `WowGuid_Format()` function (in `wow_guid_format.h`) handles the formatting.

### Object Lookup System (winkr_om.c)

Three lookup strategies, tried in order:

1. **Hash index** (O(1)): Per-thread hash tables for both GUID string and lo/hi pair lookups, rebuilt each OM tick
2. **Linear scan** (O(n) fallback): Walks all `om_object_count` entries
3. **Single-entry cache**: Last lookup result cached per thread (hit rate optimization)

**Thread safety**: Two thread-local state slots (`g_thread_state_a/b`). Seqlock prevents index rebuild during enumeration while still allowing stale-index lookups.

### Safe Memory Reading

All memory reads go through `om_ptr_ok()` which:
1. Rejects addresses below 0x10000 (null page guard)
2. Rejects addresses above canonical user-space limit (0x0000800000000000)
3. Checks page readability via `VirtualQuery` with a per-thread page cache (1024 entries, flushed every 1 second)
4. Fast-paths addresses within WoW's own module (always readable)

## 4. Mod System

### Discovery & Loading (winkr_mods.c)

**Mod directory**: `C:\mods\`

**File discovery** (two passes):
1. **Root**: `C:\mods\_*.lua` — files starting with `_` in the root
2. **Subdirectories**: `C:\mods\<subdir>\_*.lua` — files starting with `_` in each subdirectory

**Constraints**:
- Max 64 mod files (`MAX_MODS`)
- Max 1MB per file (`MAX_MOD_SIZE`)
- Only files with `_` prefix are loaded as entry points

### Loading Lifecycle

1. **DLL injection** → `SetupModLoader(moduleBase)` called from DLL entry
2. **Window discovery** → `FindGameWindowWithFallback()` — looks for `GxWindowClass` / `GxWindowClassD3d`
3. **Hook installation** → `WH_GETMESSAGE` hook on WoW's main thread
4. **Gate on in-world** → Checks `g_GameStateFlags & 0x200` (in-world flag)
5. **Trigger** → Posts `WM_LOAD_MODS` (custom message `WM_USER + 0x4D4F`)
6. **Hook proc** detects the message on main thread → calls `ReadModFiles()` + `ExecuteModsOnMainThread()`
7. **Reload detection** → If Lua state pointer changes (new `g_LuaState`), mods are reloaded

### ExecuteModsOnMainThread()

1. Resolves WoW's `luaL_loadbuffer` and `lua_pcall` trampolines
2. Reads `g_LuaState` pointer
3. Initializes vendored Lua dummynode bridge
4. **Saves and clears taint handler** (mods run as "secure")
5. Calls `CalibrateDirectStackRead(L)` for direct stack access
6. **Registers all 50 bridge functions** as Lua globals (see Section 2)
7. Executes each `.lua` file via `loadbuffer` + `pcall`
8. Prints success notification in chat
9. **Restores taint handler**

### Globals Available to Mods at Load Time

All standard WoW Lua globals plus the 50 `winkr_*` functions listed in Section 2. The taint handler is cleared during mod execution, so mods can call secure functions freely.

### Re-entry Protection

- `g_executingMods` flag prevents re-entrant calls
- Hook proc checks `g_lastLuaState` to skip redundant loads for the same Lua state
- NPC GUID safety net: automatically clears stale NPC injections after 200ms

### Key Wrapper Patterns

1. **`winkrGUID()` resolver**: All Wrappers.lua functions pass input through `winkrGUID()` which converts WoW unit tokens (e.g., `"target"`) to GUID strings via `UnitGUID()`. Strings containing `-` are assumed to already be GUIDs.

2. **Aura hook system**: Transparently intercepts `C_UnitAuras.GetAuraDataByIndex/BySpellName/ByAuraInstanceID`. For GUID-based queries, routes to `winkr_UnitAuras()`. Fixes up `_remainingSec` → `expirationTime` and resolves spell names via `C_Spell.GetSpellName()`. Cache cleared every frame.

3. **ActivePlayer type workaround**: `winkr_ObjectType` maps type 7→6. `mint.Objects()` handles this by matching ActivePlayer via GUID comparison with `UnitGUID("player")`.

4. **pcall safety**: Core.lua wraps most winkr_* calls in `pcall()` for resilience against OM race conditions.

5. **FaceDirection mouse guard**: `mint.FaceDirection()` checks `IsMouselooking()` before calling `winkr_FaceDirection()` to prevent camera snap during right-click turning.
